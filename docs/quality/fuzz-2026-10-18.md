# Fuzzing before the release (2026-10-18 and 10-19)

The places where the SDK reads what a peer sends were fuzzed twice: in
process with nim-fuzz, then for longer with libFuzzer and AddressSanitizer.
Everything a run found was fixed, and each input that found something is
kept under `tests/fuzz/corpus/<entrance>/`, where
`tests/internal/test_fuzz_regressions.nim` replays it on every test run.

How to run both: the comments at the top of `tests/fuzz/fuzz_entrances.nim`
and `tests/fuzz/libfuzzer_run.sh`. The entrances are listed in
`tests/fuzz/targets.nim`.

## In process (nim-fuzz), 200,000 inputs per entrance

macOS arm64, 2026-10-18 before 03:00 JST. These runs found five Defects,
fixed in e359c850 (MCP-SEC-WIRE-23, MCP-TASKS-7):

- a status code outside `HttpCode`'s range (`HTTP/1.1 2049`, `-5`);
- a chunk size that overflows an int, which made the decoder slice with a
  negative length;
- an icons field read from an item that is not an object;
- a task time whose minute is over 59, and one whose second is over 60:
  std/times raises a RangeDefect there instead of TimeParseError.

The last full run of 200,000 inputs per entrance before that fix found the
second-over-60 case in `clientAnswers` (`"createdAt":"2026-01-01T00:00:80Z"`,
kept as `tests/fuzz/corpus/clientAnswers/d3da1b9ca1e0f882-83.input`) and
nothing in the other 15 entrances. No full run was kept after the fix; the
run after the fix of the next section is below.

### The finding

`clientAnswers`, input kept as
`tests/fuzz/corpus/clientAnswers/e1684b9b893b43b9-libfuzzer.input`:

```
{"taskId":"t","status":"wor\x81king","createdAt":"+4052-01-01T00:00:80Z",...}
```

`taskFromJson` → `parseIsoTimestamp` → `times.parse` raised
`RangeDefect: value out of range: 80 notin 0 .. 60`. The year has a sign,
which moved the second one place to the right of where the check of
e359c850 looked; std/times accepts the sign and then raises for the second.
RFC 3339 has no sign before the year.

The fix checks the whole text as RFC 3339 (section 5.6) before std/times
reads it: `parseIsoTimestamp` now refuses anything `isDateTime` refuses.
`isDate` and `isDateTime` moved from `protocol/elicitation` into
`protocol/rfc3339`, so that tasks and elicitation share one reading of the
format. A new test of MCP-TASKS-7 gives a signed year, a five-digit year, an
hour of 25 and an offset of +24:00, and fails without the fix with the same
RangeDefect.

### After the fix

2026-10-19, macOS arm64, with the fix in the working copy:

- libFuzzer, `clientAnswers`, 1200 s: 22,408,630 inputs, coverage 3368,
  peak RSS 572 MB, no finding.
- In process, all 16 entrances, 200,000 inputs each: no finding.
- `tests/internal/test_fuzz_regressions.nim` replays the kept input of the
  finding and passes.

## What this does not cover

- Entrances not in `tests/fuzz/targets.nim`. The list was drawn from the
  places that read bytes a peer controls.
- Linux and other sanitizers (UndefinedBehaviorSanitizer, MemorySanitizer).
- refc: every run used ORC, the default.
